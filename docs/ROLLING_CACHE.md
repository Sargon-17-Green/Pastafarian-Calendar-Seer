# Rolling cache architecture

The rolling cache is a **performance artifact**, not source code, calendar authority, package identity, or release identity.

The canonical answer is always the exact Seer engine. A cache hit may avoid exact computation only after local integrity and engine-compatibility checks. Missing, stale, malformed, corrupt, or incompatible cache data is treated as a cache miss and falls through to the exact engine.

## Decision

The production design combines:

- **A. a dedicated `cache-data` branch** as the repository-owned mutable data channel; and
- **F. a stable periodic cron** that decides whether refresh is required.

`main`, npm tarballs, Git tags, GitHub Releases, and GHCR release images do not contain rolling cache data and are never modified by cache maintenance.

The cache workflow has `contents: write` only. It does not need `workflows: write`, a PAT, or `SEER_AUTOMATION_TOKEN`. It never rewrites its own schedule and never pushes to `main`.

## Alternatives considered

| Option | Result | Reason |
| --- | --- | --- |
| A. Dedicated cache-data branch | **Primary** | Cleanly separates mutable performance data from source/release identity; cheap; Git history gives audit/rollback; works without external billing. |
| B. GitHub Actions artifact / Release asset | Not primary | Workflow artifacts have retention semantics; Release assets should be immutable and version-bound. Neither is a good continuously mutable "current cache" address. |
| C. Separate package/data package | Not primary | Good distribution mechanics, but daily version churn or mutable dist-tags create confusing npm semantics; offline installs also pin an inevitably stale snapshot. |
| D. Object storage/CDN | Good future mirror | Best serving/bandwidth model at scale, but introduces an external service, credentials/billing/operations, and is unnecessary for the current repository-owned cache volume. |
| E. Bot PR to main | Rejected | Better than direct push, but still makes time-dependent cache bytes part of source history/package review and causes needless CI/package churn. |
| F. Stable periodic cron | **Scheduler** | Refresh retries are independent. One failed run cannot delete the next trigger. The job can cheaply no-op when the cache is already current. |

A future CDN may mirror a verified `cache-data` commit, but the mirror must remain optional and must not become semantic authority.

## Data channel

`cache-data` contains only:

```text
index.json
calc/<calculation-jdn>.json
calc/<calculation-jdn>.json
calc/<calculation-jdn>.json
```

The index records:

- cache schema;
- exact engine fingerprint;
- astronomy-model fingerprint;
- producing source commit, when generated by CI;
- active calculation JDN;
- four Venus-boundary instants;
- three cache descriptors with SHA-256 checksums.

Each calculation-day cache contains 366 target-day records. Descriptor paths are fixed to `calc/<calcJdn>.json`; arbitrary relative paths are rejected.

The branch advances by normal commits. It is not force-pushed during routine refresh. Historical commits therefore provide an audit trail and rollback source.

## Refresh policy

`.github/workflows/precompute-seer-cache.yml` runs on a fixed six-hour schedule and by manual dispatch.

The job:

1. checks out current `main`;
2. restores the current `cache-data` snapshot, if the branch exists;
3. calculates the current engine and astronomy fingerprints and active calculation day;
4. no-ops when the existing snapshot is complete and compatible;
5. otherwise builds the exact batch engine;
6. reuses still-valid calculation-day files and computes only missing/incompatible days;
7. validates structure, fingerprints, paths, SHA-256 checksums, and source commit;
8. verifies that no `HANDOFF_*` file is present;
9. commits only `index.json` and `calc/*.json` to `cache-data`.

The three-day calculation horizon means a delayed refresh does not immediately remove cache coverage at a Venus boundary. If refreshes fail long enough for coverage to expire, canonical queries still fall back to the exact engine.

## Runtime contract

The default runtime may look for a cache directory, but the directory is optional.

Selection order:

1. explicit query option `generatedDir`;
2. `SEER_CACHE_DIR`;
3. the historical default `generated/` path, which may not exist.

On every potential hit the loader verifies:

- index/descriptor shape;
- descriptor path confinement;
- file SHA-256;
- cache record structure and continuity;
- exact engine fingerprint compatibility with the installed/source runtime.

Any failure is a cache miss. The exact engine then determines the answer. Cache corruption or staleness therefore cannot substitute a different canonical answer.

The runtime does **not** auto-download cache data. This prevents network availability, DNS/CDN state, or a mutable remote pointer from becoming part of request semantics.

## npm users

The npm package contains the exact runtime source/data and build scripts, but no rolling cache snapshot.

For local exact queries:

```bash
npm explore pastafarian-calendar-seer -- npm run build:native
```

An operator may separately place a verified cache-data checkout on disk and set:

```text
SEER_CACHE_DIR=/path/to/cache-data
```

If that directory disappears or becomes invalid, queries use the exact engine.

Browser users of `pastafarian-calendar-seer/client` are unaffected because the browser package talks to a remote HTTP service.

## Source checkouts

A clean source checkout is deterministic with respect to Git: cloning `main` no longer yields different rolling bytes depending on the day.

Repository tests create temporary cache fixtures. Cache generation defaults to `.cache-build/rolling`, which is ignored by Git.

Maintainers can validate a separately checked-out cache snapshot with:

```bash
node precompute/validate-generated.mjs --generated-dir=/path/to/cache-data
```

## Containers

Release images remain immutable and do not bake in rolling data.

A deployment can run entirely on the exact persistent engine, or mount cache data read-only and set `SEER_CACHE_DIR`. Updating the mounted cache is an operational optimization and does not require rebuilding or retagging the image.

If an orchestrator refreshes the mounted directory, it should publish a complete verified directory as one deployment unit rather than editing files in place.

## Security and permissions

The refresh workflow uses only the repository-scoped `GITHUB_TOKEN` with:

```yaml
permissions:
  contents: write
```

It has no `workflows: write` permission and no long-lived cache secret.

The supply-chain audit rejects:

- `SEER_AUTOMATION_TOKEN`;
- `[skip ci]` in the cache workflow;
- generated Venus schedule markers/self-rewrite logic;
- a cache workflow that pushes `main`;
- tracked `generated/` rolling data;
- tracked `HANDOFF_*` files.

The cache branch is not release authority. A compromised cache channel must still pass local checksum/shape/engine compatibility checks; operators requiring stronger origin authentication can pin a specific cache-data commit or mirror verified commits into controlled storage.

## Failure recovery and rollback

A refresh failure leaves the previous `cache-data` commit untouched. The stable cron continues to run every six hours.

If a bad cache commit is discovered, do not rewrite a release or source tag. Generate a new verified cache snapshot from a known-good source commit and publish it as a new `cache-data` commit. Consumers can also pin an older cache-data commit while the repair is prepared.

If the cache branch is deleted, the next successful workflow run bootstraps it as an orphan data branch.

## Reproducibility and release semantics

Rolling bytes are intentionally not reproducible across wall-clock time, so they are excluded from reproducible source/package artifacts.

Release reproducibility now covers only versioned source/runtime artifacts. Cache reproducibility is scoped separately: for a fixed source commit, calculation day and generation inputs, the exact records and checksums must agree.

No published release is altered by this migration. The first source release containing this architecture must use a new version and must not be published until the full verification matrix is green.

## Migration from the legacy mechanism

The migration removes:

- tracked `generated/index.json`;
- tracked `generated/calc/*.json`;
- self-modifying schedule code;
- workflow schedule rewrite tests;
- rolling cache files from `package.json`;
- `npm run validate:cache` as an installed-package requirement;
- release/container checks that require bundled rolling data.

After the new workflow is merged and verified:

1. manually dispatch it once to bootstrap `cache-data`;
2. verify that a second run no-ops when no refresh is required;
3. verify a forced/day-transition refresh creates only a `cache-data` commit;
4. remove the repository secret `SEER_AUTOMATION_TOKEN` because no workflow references it;
5. do not publish a release until normal source CI, package tests, container tests, cache tests, and supply-chain checks all pass.

## Storage and bandwidth

The branch stores only three current JSON cache files per commit. Git delta compression makes daily history modest for the current payload size. Source clones do not fetch `cache-data` unless explicitly requested, so ordinary npm/source/container bandwidth no longer includes rolling data.

If traffic to cache-data becomes material, the same verified directory format can be mirrored to object storage/CDN without changing calendar semantics or the local validation contract.
